Context

See proposal.md (Why). A maintainer of finos/morphir moves the OpenSpec pin from 1.14.3 to 2.2.0 and runs mise run openspec:setup. The tools CLI parses openspec --version into SupportedOpenSpec (decision VER-1 of the archived change support-openspec-1-16-setup). The support table is [Exact(1, 14, 3), Series(1, 16)], so setup prints openspec-ext: Setup requires OpenSpec 1.14.3 or 1.16.x and exits with 1.

If the table accepted 2.2.0 and nothing else changed, setup would run openspec init --tools … --profile core --no-animation. OpenSpec 2.1 and later install the skills for every project on the machine for that command. Setup sets XDG_CONFIG_HOME to a temporary directory but keeps HOME, so the skills would go to the maintainer's ~/.agents/skills/, and the repository would keep its old skills.

Goals and non-goals

  • Goal: setup accepts 2.2.x and keeps the skills in the repository, with the rule in the typed version.
  • Goal: setup with 1.14.3 and 1.16.x runs the same command as before.
  • Non-goal: a choice of global skills. The repositories check in their skills, so that hosted agents and reviewers see the same files.
  • Non-goal: a change to the OpenSpec 2 skill layout. Setup takes the files that openspec init writes.

Decisions

VER-4. 2.2 as a patch series

The support table becomes [Exact(1, 14, 3), Series(1, 16), Series(2, 2)], and supported_openspec becomes "1.14.3, 1.16.x or 2.2.x". As in VER-2, OpenSpec patch releases fix validation and do not change the schema format or the init options that setup uses. 2.0.x and 2.1.x are not accepted: they were not tested, 2.1.0 needs Git and GitHub to install skills (OpenSpec changelog), and no consumer pins them.

Alternative: accept every 2.x release. Rejected: a minor release can change init again, as 2.1 did. Each minor series needs a proof (VER-6).

VER-5. The version selects the init scope

SupportedOpenSpec::scope_arguments gives ["--scope", "project"] for major version 2 and later, and no arguments for 1. host.init_arguments builds the full argument list from it, and setup_with passes the list to run_init. The acceptance tests then check the exact arguments for each version, without an OpenSpec install.

pub fn init_arguments(openspec : @extension.SupportedOpenSpec) -> Array[String]

pub async fn setup_with(
  repository : @extension.RepositoryPath,
  version_in : async (String) -> String?,
  run_init : async (String, String, Map[String, String], Array[String]) -> Int32,
) -> Unit

Alternative: always pass --scope project. Rejected: OpenSpec 1 refuses an unknown option, so consumers on 1.14.3 and 1.16.x would break. Alternative: set HOME to the temporary directory. Rejected: the skills would then be written to the temporary directory and removed with it.

VER-6. Proof before support

The test of 2026-11-25 ran the built mission-control-tools openspec setup with OpenSpec 2.2.0 against copies of Mission Control and finos/morphir:

The skill layout is the OpenSpec 2 layout: one copy of each core skill in .agents/skills/, a link to it in .claude/skills/ and .grok/skills/, and the new openspec router skill with its references/ folder. OpenSpec removes the copies that it generated in .cursor/, .gemini/, .github/ and .opencode/, because those agents read .agents/skills/. The same setup with OpenSpec 1.14.3 against Mission Control exits with 0 and changes no file.

Risks and trade-offs

  • [A Windows checkout without core.symlinks gets a text file for each link] → OpenSpec replaces it with a plain copy at the next openspec update. CI does not read the agent skills.
  • [A later 2.2 patch changes the init output or the schema rules] → openspec check --bundle and openspec validate --all --strict in the consumer show it; a tools patch release can then narrow the series.
  • [The refusal message changes] → Scripts that match the old text break. The exit code stays 1.
  • [setup_with takes a different run_init] → moonrockz/openspec-ext is not published yet, and only the tests call setup_with.

Migration plan

Release in tools-v0.1.3. A consumer moves its OpenSpec pin to 2.2.0 and its tools pin to 0.1.3, then runs mission-control-tools openspec install, mise run openspec:setup and mise run openspec:verify, and commits the new skill layout. To roll back, pin the old OpenSpec version and tools 0.1.2 again, and run setup.
