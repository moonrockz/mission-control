Shared OpenSpec extensions

2026-10-28 | Bead moonbase-933

Context | Decisions | Migration | Risks

Context

See proposal.md for motivation and specs/openspec-extensions/spec.md for the contract.

Decisions

EXT-1. A packaged MoonBit tool owns the bundle

The pure package holds the schema and templates as raw multiline strings. The host boundary installs them. A cmd package runs through moonx after publication or moon run from source. This avoids runtime paths into a source checkout and works with any target repository.

EXT-2. Project-local snapshots with an ownership lock

Consumers commit normal OpenSpec files. A lock records module version and SHA-256 digests. Installs preflight all files, preserve unknown files, refuse changed managed files, and write the lock last. A source checkout is sufficient to update candidates before publication. No unpublished registry pin is required.

EXT-3. Repository policy stays local

The shared workflow contains no tracker hierarchy or repository IDs. Project configuration retains context and artifact rules. HTML uses inline CSS and no external resources, so archive does not change asset paths. Existing Markdown changes retain their spec-driven metadata.

EXT-4. Schema templates are assets

The OKF profile gains a default asset classification hook. Any active profile can keep a Markdown path opaque. OpenSpec reserves schemas/ for configuration and uses that classification during both import and export. This prevents template prose from becoming knowledge concepts and preserves their exact bytes.

Migration

Save the three prior schema copies locally, move their policy into repository configuration, then install and validate the common bundle. Initialize the five requested repositories and migrate Moon-Lander and Mission Control defaults. Preserve changes, accepted specifications and ongoing work. Publication follows the existing release process; consumer release pins follow actual publication.

Risks

Local schema edits require review before update. Unsupported YAML layouts fail before writes. Interrupted filesystem writes can leave partial output; unchanged owned files can be repaired by rerunning install, and the previous lock remains until success. Concurrent installs in one repository are not supported.
