Context

See proposal.md (Why). Today setup_with in apps/openspec-ext/host/install.mbt compares the text of openspec --version with the constant "1.14.3". A mismatch raises InstallError::OpenSpecVersion, and the tools CLI prints openspec-ext: Setup requires OpenSpec 1.14.3 and exits with 1. Setup then runs openspec init --tools … --profile core --no-animation with an isolated configuration directory. Setup does not read or write the managed html-design files.

Goals and non-goals

  • Goal: setup accepts 1.14.3 and 1.16.x, and the rule is in one typed place in the pure package.
  • Goal: the version text is parsed one time, at the boundary where openspec --version returns.
  • Non-goal: a configurable version list. Each supported version needs a proof (VER-3), so a release of the tools CLI adds it.
  • Non-goal: the found version in the refusal message. The message stays one fixed text, as the spec gives it.

Decisions

VER-1. A type for a supported OpenSpec version

The pure package moonrockz/openspec-ext gets SupportedOpenSpec, a struct with a private @contracts.Version. Its smart constructor parses the text with @contracts.Version (three numbers, no leading zeros) and then requires 1.14.3 or major 1 and minor 16. A failure is the typed OpenSpecVersionError::UnsupportedOpenSpec(text). The constant supported_openspec ("1.14.3 or 1.16.x") gives the text for the message.

pub fn SupportedOpenSpec::SupportedOpenSpec(
  text : String,
) -> SupportedOpenSpec raise OpenSpecVersionError

setup_with keeps its signature: the injected version_in still returns the raw text or None, because that is the process boundary. setup_with parses it into SupportedOpenSpec and maps a failure or None to InstallError::OpenSpecVersion.

Alternative: a list of exact version strings in host. Rejected: it keeps the rule as a string compare in the I/O package, and a 1.16 patch release would need a tools release.

VER-2. 1.16 as a patch series

Setup accepts every 1.16 patch release, not only 1.16.0 and 1.16.1. finos/morphir-scala and finos/morphir-gleam already pin different 1.16 patches, and Renovate moves them. OpenSpec patch releases fix validation and do not change the schema format or the init options that setup uses. 1.14 stays exact (1.14.3), because Mission Control and the other consumers pin it and the earlier 1.14 patches were not tested. 1.15 is not accepted: no consumer pins it and it was not tested.

Alternative: accept exact 1.16.0 and 1.16.1 only. Rejected: the next 1.16 patch would break openspec:setup for these consumers until a tools release.

VER-3. Proof before support

The test of 2026-11-07 ran each of OpenSpec 1.14.3, 1.16.0 and 1.16.1 against a copy of Mission Control:

The automated tests inject the version text, so they do not need an OpenSpec install. Before the merge, the same proof runs again through the built mission-control-tools openspec setup with 1.16.0 and 1.16.1. No CI job is added.

Risks and trade-offs

  • [A later 1.16 patch changes the init output or the schema rules] → openspec check --bundle and openspec validate --all --strict in the consumer show it; a tools patch release can then narrow the series.
  • [The refusal message changes] → Scripts that match the old text break. The tools CLI is at 0.1.x, and the message is for people; the exit code stays 1.

Migration plan

Release in tools-v0.1.1. Consumers on OpenSpec 1.16.x move their mise entry to 0.1.1 and run mission-control-tools openspec install and mise run openspec:setup. To roll back, pin 0.1.0 again; 1.14.3 consumers see no change.
