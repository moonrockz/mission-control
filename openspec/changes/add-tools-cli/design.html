Context

See proposal.md for the reason. The current state:

  • apps/openspec-ext (module moonrockz/openspec-ext) has a pure bundle (bundle.mbt, extension.mbt), a host package with install, check and setup (host/install.mbt), and a command in cmd. The module is not published yet.
  • The bundle has nine files. Two of them are scripts/openspec-ext.mbtx and its feature. Consumers run the script with moon run --target wasm; the host setup also runs the script.
  • The script check is a snapshot check: it compares the files with the lock digests and does not know a tool version. The host check compares the lock text with the bundle of its own version.
  • The lock is format 1 and records "module": "moonrockz/openspec-ext" and the workspace version.
  • All workspace modules share one version (scripts/versions.mbtx). The Release workflow builds the main CLI only: five native archives, two wasm files and checksums.txt, with no attestations.
  • A zig-cross build of apps/openspec-ext/cmd with moonbitlang/async 0.22.5 passes for linux-x64, linux-arm64, darwin-arm64 and darwin-x64 (tested on 2026-11-07). moonbitlang/async lists Windows support through IOCP.

Goals and non-goals

Goals: one binary that a consumer pins by version and checksum; the same check and setup results as the script; a release that does not depend on the main CLI release; a migration that a consumer does in one pull request.

Non-goals: new OpenSpec features in the bundle; a plugin system for tool groups; automatic edits of consumer mise files; a release-prepare automation for the tools family (the release is rare; the steps are in the README).

Decisions

NAME-1. Module, binary and command names

Module moonrockz/mission-control-tools in apps/tools. The executable is mission-control-tools (mission-control-tools.exe on Windows). The OpenSpec commands are in the group openspec.

  • The name tells a reader that the tool comes from Mission Control and is not the product CLI. The group leaves space for other repository utilities without a new binary.
  • Alternatives: openspec-ext as the binary name (ties the binary to one area, and the name is already the library); mctools (short, but nobody can guess the source); a tools subcommand of mission-control (Damian rejected it on 2026-11-07).

CMD-1. Command grammar

mission-control-tools help | --help | -h
mission-control-tools version [--json]
mission-control-tools openspec check [--bundle] [--json] [REPOSITORY]
mission-control-tools openspec install [REPOSITORY]
mission-control-tools openspec setup [REPOSITORY]

The parser is pure. It parses the arguments one time into a Command enum (Help, Version(Format), OpenSpec(OpenSpecCommand, RepositoryPath)), with CheckLevel (Snapshot, Bundle) and Format (Text, Json) as enums, not booleans. Options and the path can come in any order after the command. A path that starts with - is an unknown option. The default path is .. RepositoryPath keeps its current rules (nonempty, no NUL, no line break).

CMD-2. Two check levels

LevelChecksUse
check (snapshot)Lock format and file set; each managed file against its lock digest; default schema.The same result as the script. It does not depend on the binary version, so a consumer can run any later binary on an old snapshot.
check --bundleThe snapshot checks, then the lock tool and version against the binary, and each managed file against the bundle in the binary.Consumer openspec:check. It fails when the mise pin moves and nobody runs install, so the pin and the lock stay together.

The bundle level is the current host check, extended with the snapshot problems. Alternative: only one strict check. Rejected: the task needs the script behavior, and a version-free check is useful when a consumer tests a new binary before it moves the lock.

CMD-3. Messages and exit codes

  • Exit codes: 0 success, 1 failure, 2 usage error, from one ExitCode value in the tools CLI. A usage error stops before any file read.
  • Success lines: html-design snapshot: OK for check and setup (as the script); html-design: OK (mission-control-tools X.Y.Z) for install.
  • Problem lines: openspec-ext: <text> on standard error. The texts are the script texts. The script printed them through fail, which added Failure(<file>:<line> FAILED: …); the binary prints the text only. The openspec-ext: prefix stays, so log searches and consumer documentation keep working.
  • New texts for cases where the script stopped with a raw file system error: Missing file: <path>, and the format 1 message of openspec-extensions.
  • The core returns all problems in a fixed order (lock, files in bundle order, config). The script stopped at the first; for one problem the output is the same.

CMD-4. JSON reports

The repository's agent-facing tools (the OpenSpec CLI, the morphir CLI) give --json on read commands. The tools CLI does the same for check and version. install and setup write files and stream the output of openspec init, so they have no JSON mode. The JSON goes to standard output; the exit code does not change.

{
  "tool": "mission-control-tools",
  "version": "0.1.0",
  "command": "openspec check",
  "level": "bundle",
  "repository": "/work/morphir",
  "ok": false,
  "problems": [
    { "code": "drift", "path": "openspec/schemas/html-design/templates/design.html",
      "message": "Extension drift: openspec/schemas/html-design/templates/design.html" }
  ]
}

Problem codes: unsupported-lock, legacy-lock, file-set, missing-digest, missing-file, drift, schema, tool-version, bundle-drift. Each code is a case of a Problem enum; the code and the message come from the case.

CORE-1. Reuse of openspec-ext

  • moonrockz/openspec-ext stays the owner of the bundle, the lock and the checks. It gains a pure check_snapshot(lock, files, config, level) that returns problems. The inputs are the texts that the host read (String? for each path), so the core has no I/O and the acceptance tests use fixtures.
  • openspec-ext/host reads the files, calls the core, and does the writes of install and the process of setup. It takes the tool identity (module and version) as an argument, so the library does not import the tools module.
  • apps/openspec-ext/cmd is removed. Two commands with the same job would drift. The module is not published yet, so no user loses a command.
  • apps/tools has the argument parser, the output formats and main. It is native and wasm only, like the host (moonbitlang/async has no JS or wasm-gc file system). The release builds native only.

SET-1. Setup in the binary

The script's setup_with moves to the host: it makes a temporary directory, writes openspec/config.json with the core profile, skills delivery and the telemetry notice, runs openspec init --tools agents,codex,claude,github-copilot,cursor,grok,gemini,opencode --profile core --no-animation in the repository with XDG_CONFIG_HOME and OPENSPEC_TELEMETRY=0, and removes the directory with defer. The process runner is a function argument, so the test checks the environment and the cleanup without OpenSpec. Setup runs the snapshot check first and does not install, as the script did. The current host setup that installs and then runs the script goes away.

LOCK-1. Lock format 2 and retired files

{
  "format": 2,
  "extension": "html-design",
  "tool": "moonrockz/mission-control-tools",
  "version": "0.1.0",
  "files": {
    "openspec/schemas/html-design/schema.yaml": "…",
    "openspec/schemas/html-design/templates/proposal.md": "…",
    "openspec/schemas/html-design/templates/spec.md": "…",
    "openspec/schemas/html-design/templates/design.html": "…",
    "openspec/schemas/html-design/templates/tasks.md": "…",
    "openspec/schemas/html-design/NOTICE": "…",
    "openspec/schemas/html-design/LICENSE": "…"
  }
}
  • version is the version of the tools CLI that wrote the lock. A consumer reads one number in its mise file and one in its lock, and the bundle check compares them.
  • The format number changes because the file set and the owner field change. A format 1 reader (an old script copy) rejects format 2, which is correct: the copy is gone after the migration.
  • install accepts a previous lock of format 1 or 2. For a file that the previous lock records and the bundle does not manage (the script and its feature), install deletes it when its digest matches the previous lock and fails before any write when it does not. A missing retired file is not a problem. Install deletes the retired files after it writes the managed files and before it writes the lock, so an interrupted run repeats safely.
  • The lock is parsed at the boundary into a typed Lock (format, tool, version, digests as FileDigest). The checks use the typed value.

VER-1. Tools version family

  • apps/tools/moon.mod is the source of the tools version. The first version is 0.1.0. The binary reads its version from one constant in apps/tools, through a Version value.
  • scripts/versions.mbtx gets a second family. check checks the workspace family (every member except apps/tools) and the tools family (apps/tools/moon.mod, the version constant, its test, and openspec/extensions.lock.json). set X.Y.Z changes the workspace family only. set-tools X.Y.Z changes the tools family only. The sibling imports in apps/tools/moon.mod (openspec-ext, contracts) belong to the workspace family.
  • The tools module is not in the publish lists. Alternative: publish to mooncakes.io for moonx. Rejected for now: it brings back the toolchain coupling, and a mooncakes.io version is permanent.

REL-1. Release workflow and tags

  • New workflow .github/workflows/release-tools.yml. Triggers: a push to main that changes apps/tools/moon.mod or apps/tools/CHANGELOG.md, and workflow_dispatch with dry_run. It has no pull_request and no merge_group trigger. Concurrency group release-tools.
  • Jobs: plan, validate (lint, the tools and openspec-ext tests on wasm and native, openspec:check, versions), build-windows (native on windows-latest), build (zig-cross for four targets, then pack), smoke (five runners: check out the repository, run version and openspec check --bundle .), release.
  • scripts/release-tools.mbtx has plan, notes X.Y.Z, github X.Y.Z and status. The plan reads the version from apps/tools/moon.mod, the run trigger, main ancestry, the state of the release tools-vX.Y.Z and the section in apps/tools/CHANGELOG.md, as typed values like the main release script. github creates the release with --target the commit, so GitHub creates the tag; a rerun uploads only the missing assets.
  • scripts/dist.mbtx gets a product argument (cli, the default, or tools). A Product enum gives the package, the executable name, the archive prefix, the output directory (dist/ or dist-tools/) and whether wasm files are built. The main CLI outputs do not change.
  • The main Release workflow keeps tags: ['v*']. GitHub matches tag filters from the start of the name, so tools-v0.1.0 does not start it.
  • No attestations, as in the main release. A later change can add actions/attest-build-provenance to both releases.

REL-2. Consumer mise entry

The release notes end with this entry, generated by release-tools.mbtx notes from checksums.txt:

[tools."http:mission-control-tools"]
version = "0.1.0"
bin_path = "."

[tools."http:mission-control-tools".platforms]
linux-x64 = { url = "https://github.com/moonrockz/mission-control/releases/download/tools-v0.1.0/mission-control-tools-linux-x64.tar.gz", checksum = "sha256:…" }
linux-arm64 = { url = "https://github.com/moonrockz/mission-control/releases/download/tools-v0.1.0/mission-control-tools-linux-arm64.tar.gz", checksum = "sha256:…" }
macos-arm64 = { url = "https://github.com/moonrockz/mission-control/releases/download/tools-v0.1.0/mission-control-tools-darwin-arm64.tar.gz", checksum = "sha256:…" }
macos-x64 = { url = "https://github.com/moonrockz/mission-control/releases/download/tools-v0.1.0/mission-control-tools-darwin-x64.tar.gz", checksum = "sha256:…" }
windows-x64 = { url = "https://github.com/moonrockz/mission-control/releases/download/tools-v0.1.0/mission-control-tools-windows-x64.zip", checksum = "sha256:…", format = "zip" }
# No Windows arm64 build; Windows on Arm runs the x64 build under emulation.
windows-arm64 = { url = "https://github.com/moonrockz/mission-control/releases/download/tools-v0.1.0/mission-control-tools-windows-x64.zip", checksum = "sha256:…", format = "zip" }
  • The http backend pins the exact URL and checksum for each platform. It is the same form that consumers use for the MoonBit pin, it needs no GitHub API call (no rate limit in CI), and its key does not collide with github:moonrockz/mission-control, which installs the main CLI.
  • Alternative: github:moonrockz/mission-control with version_prefix = "tools-v" and an asset_pattern. It verifies the GitHub asset digest, but one repository can have only one such key in a mise file, and the main CLI already uses it.
  • The entry is proved before release with file:// URLs to the locally built archives and their real checksums (mise accepts file:// for the http backend).

REL-3. Dry run without new pull request jobs

The task forbids new qualification jobs in pull request and merge queue CI. GitHub runs workflow_dispatch only for a workflow that is on the default branch, so the new workflow cannot have a dispatch dry run before it merges. Before the merge: a local dry run (plan with DRY_RUN=true, cross-build, pack, checksums, the mise entry, smoke on macOS arm64, and the morphir migration proof). The existing Release workflow runs on this pull request because it changes scripts/dist.mbtx and scripts/versions.mbtx; that run proves that the main CLI outputs do not change. After the merge and before the first tag: gh workflow run release-tools.yml -f dry_run=true builds all five platforms and runs smoke, including Windows.

Migration plan

For each consumer, in one pull request:

  1. Add the [tools."http:mission-control-tools"] entry from the release notes to .config/mise/config.toml and run mise install.
  2. Run mission-control-tools openspec install .. It deletes the unedited scripts/openspec-ext.mbtx and scripts/features/openspec_ext.feature, keeps the schema files, and writes the format 2 lock.
  3. Change the tasks: 
    [tasks."openspec:check"]
run = "mission-control-tools openspec check --bundle"

[tasks."openspec:setup"]
run = "mission-control-tools openspec setup"

[tasks."openspec:validate"]
run = ["openspec schema validate html-design", "openspec validate --all --strict"]

[tasks."openspec:verify"]
run = ["mise run openspec:check", "mise run openspec:validate"]
    Remove openspec:test and the moon update step that existed only for the script. Remove the script from any script test runner.
  4. Run mise run openspec:verify. Commit the lock, the mise file and the deletions.

Rollback: revert the pull request. The format 1 lock and the script return with it. Mission Control keeps the change history, so a later install of the previous bundle is not needed.

In Mission Control: openspec:install, openspec:check and openspec:setup run moon run apps/tools -- openspec … from source; the lock moves to format 2; the script, its feature and its entry in the script tests are removed.
